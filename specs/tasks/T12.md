# T12 · Run orchestration

- **Model**: sol
- **Tier**: strict
- **Depends on**: T11
- **Goal**: The outer LangGraph graph for one run: start the run, fan out one T11 worker per check with at most 5 in parallel, share one database-backed budget, survive a crash via the Postgres checkpointer, pause for human review when any finding needs it, and finish with the right run status.

## Entry points (`run_graph.py`)
- `async run_run(engine: AsyncEngine, run_id: UUID, *, deps: RunDeps) -> RunStatus` — start or resume a run until it ends or pauses.
- `async resume_run(engine, run_id, *, deps) -> RunStatus` — continue a run that is `waiting_review` (called after reviews, T20).
- `RunDeps`: `llm`, `models`, `embedder | None`, `checkpointer`, `seed: int = 20261025` (fixed, D18/D48), `max_concurrency: int = 5` (D45), `comparer: Comparer` (default no-op), `emit: EventSink` (default no-op), `step_cap`, `token_cap`, `max_output_tokens`, `tool_timeout_s` (passed through to T11).
- The LangGraph `thread_id` is `str(run_id)`.

## Graph (D3) — nodes `start`, `load_checks`, `check_worker`, `compare`, `review_gate`, `finalise`
1. **`start`**: load the run row. Refuse (status `failed`, `error` set, `finished_at` set, no LLM call) when: `method` is not `A` or `C` (`method_not_supported`; B and LC come in T16/T17), `check_set_version` differs from the loaded check set's `version` (`check_set_changed`), or `prompt_sha256` differs from `cda.agent.prompts.prompt_sha256()` (`prompt_changed`, D39). Otherwise a `queued` run becomes `running` with `started_at`; a `running` run (resume after crash) stays `running`. A `cancelled` run goes straight to `finalise`.
2. **`load_checks`**: the check ids of the check set **minus those that already have a `findings` row for this run** (so a resumed run never redoes or duplicates a stored check). Fan out with `Send("check_worker", {"check_id": …})` for each (D1, D16).
3. **`check_worker`** (one per check; at most `max_concurrency` at a time via the graph config, D45):
   - opens **its own** connection from `engine` (asyncpg cannot run two queries at once on one connection) and its own `ToolContext` through T11;
   - if the run is no longer `running` (cancelled / failed) → store `not_checked` with reason `cancelled` (or skip storing if `failed`) without any LLM call;
   - otherwise `run_worker` (T11) with the run's `method`, `model_key`, `created_by` as `user_id`, `pack_id`, the shared `RunBudget`, and the deps' caps; then `store_finding` and commit;
   - a `not_checked` result caused by the run being cancelled gets reason `cancelled` instead of `budget_exhausted`;
   - `LLMAuthError` (D21): mark the run `failed` with `error = "llm_auth"` and `finished_at` immediately (separate committed statement, so other workers' next `reserve` fails), then re-raise so the graph stops.
4. **`compare`**: `await deps.comparer(conn, run_id)` once all workers finished (T13 plugs in here; default does nothing).
5. **`review_gate`**: if any finding of the run has status `needs_review` and no `reviews` row yet → set run status `waiting_review` and call LangGraph `interrupt({"run_id": …, "needs_review": [check ids]})`. On resume it checks again: still unreviewed → interrupt again; all reviewed → continue.
6. **`finalise`**: `cancelled` stays `cancelled`; otherwise status `final`; set `finished_at`. (Draft = `running`/`waiting_review`, Final = `final`, per requirements.)
- Any other exception escaping the graph → run `failed`, `error` = exception type name (no message), `finished_at` set; `run_run` returns `failed` instead of raising, except `LLMAuthError`, which also returns `failed` after the run is marked.

## Budget (`run_budget.py`, D22)
`RunBudget(engine, run_id)` implements T11's `Budget`, shared by all workers of the run:
- `reserve(amount)`: one atomic statement on its own short transaction, committed immediately: `UPDATE runs SET spent_usd = spent_usd + :amount WHERE id = :run AND status = 'running' AND spent_usd + :amount <= budget_usd RETURNING spent_usd`. No row → `False`; it also remembers whether the refusal was because the run is not `running` (`cancelled` / `failed`) or because of the limit.
- `settle(reserved, actual)`: `spent_usd = spent_usd - reserved + actual`, committed immediately. `spent_usd` never goes below 0.
- Five workers reserving concurrently can never push `spent_usd` above `budget_usd`.

## Checkpointer (`checkpoint.py`, D23)
`async open_checkpointer(database_url) -> AsyncPostgresSaver` (async context manager): converts the SQLAlchemy URL (`postgresql+asyncpg://…`) to a libpq URL for psycopg, opens `AsyncPostgresSaver`, runs its idempotent `setup()` (its own tables, not managed by Alembic). Never logs the URL.

## Hooks (`hooks.py`)
- `Comparer = Callable[[AsyncConnection, UUID], Awaitable[None]]`, `noop_comparer`.
- `EventSink = Callable[[UUID, str | None, str, dict], Awaitable[None]]` (`run_id`, `check_id`, `type`, `payload`), `noop_sink`. Emit `run_started`, `check_started`, `check_finished` (`status`), `run_waiting_review`, `run_final`, `run_failed` (`error`), `run_cancelled`. T14 writes them to `run_events` + NOTIFY.

## Failing tests to write first (strict: every case its own test, seen failing first; all `db`)
Test setup: these tests need **committed** data and several connections, so use an `AsyncEngine` on `pg_url` with migrations at head, seed users/team/pack/documents/units (with `seq`, context headers, `HashEmbedder` embeddings) and a `check_sets` row matching `load_check_set()`, and clean up with `TRUNCATE … CASCADE` (plus the checkpointer's tables) after each test. Use a scripted fake LLM that picks its script **by check id** (parse `Check <id>:` from the second message), since 15 workers run in an unpredictable order; default script = one search + `submit_finding(no_evidence_found)` or a verified `evidence_found`, as each test needs.

Statuses and start:
1. A `queued` run with all 15 checks scripted → status `final`, 15 `findings` rows, `started_at`/`finished_at` set, `spent_usd` equals the sum of `llm_calls.cost_usd`
2. Method `B` (and `LC`) → `failed`, `method_not_supported`, no LLM request
3. `check_set_version` mismatch → `failed`, `check_set_changed`; `prompt_sha256` mismatch → `failed`, `prompt_changed`
4. A run already `cancelled` before start → stays `cancelled`, no LLM request, `finished_at` set

Concurrency and fan-out:
5. Never more than 5 workers inside the LLM at once (the fake LLM counts concurrent `complete` calls with an `asyncio` gate), and at least 2 do run concurrently
6. With `max_concurrency=1` the workers run one at a time
7. Each worker uses its own connection (no "another operation is in progress" errors) — covered by 1 and 5; additionally assert all 15 findings have distinct `check_id`

Budget (D22):
8. Budget for about 3 checks → the first checks complete, the rest are `not_checked` with `budget_exhausted`; `spent_usd ≤ budget_usd` at the end
9. Five concurrent `reserve` calls on a nearly-full budget → only the ones that fit succeed (direct `RunBudget` test with `asyncio.gather`)
10. `settle` with actual < reserved lowers `spent_usd` by the difference; never below 0
11. Setting the run to `cancelled` mid-run → later checks `not_checked` with reason `cancelled`; final run status `cancelled`

Auth failure (D21):
12. One check's script raises `LLMAuthError` → run `failed` with `error = "llm_auth"`; checks not yet started make no LLM call; `run_run` returns `failed`

Resume (D23):
13. Crash simulation: a scripted fake raises a custom `SimulatedCrash` (not an `LLMError`) after N checks have been stored, which propagates out of the graph; a fresh `run_run` with the same `thread_id` and checkpointer completes the run, the previously stored checks are not re-run (no new `llm_calls` for them) and there are exactly 15 findings. (For this test only, `run_run` lets `SimulatedCrash` propagate — inject it via a `RunDeps` field `reraise: tuple[type[BaseException], ...] = ()`.)
14. `load_checks` skips checks that already have a finding (pre-insert two findings, run → 13 workers start)

Human review interrupt:
15. One check ends `needs_review` → run `waiting_review`, graph interrupted; `resume_run` without a review → still `waiting_review`
16. After inserting a `reviews` row for that finding, `resume_run` → `final`
17. No `needs_review` findings → no interrupt, straight to `final`

Hooks and events:
18. `comparer` is awaited exactly once, after all 15 findings are stored
19. `emit` receives `run_started`, 15 `check_started` / `check_finished`, and `run_final` (or `run_waiting_review`) in a valid order
20. Unexpected exception inside `compare` → run `failed`, `error` = exception type name; message text not stored
21. `open_checkpointer` works with the `postgresql+asyncpg://` test URL and `setup()` is idempotent (call twice)
