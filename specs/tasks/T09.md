# T09 · Database-level permissions (read-only tool role + RLS)

- **Model**: sol
- **Tier**: strict
- **Depends on**: T08
- **Goal**: A second, independent permission layer under the T08 tools: every tool call runs as a read-only Postgres role whose row-level security only shows rows of the caller's teams, so a bug in a tool query cannot leak another team's documents.
- **Design**: `02-design.md` §4 (permissions paragraph), §6; decisions D29, D61 (and D28: tools are read-only)
- **Libraries**: sqlalchemy, alembic (no new packages)

## Migration 0005
- Role `cda_tool`: `NOLOGIN`, created only if it does not exist (roles are cluster-wide; use a `DO` block). `GRANT cda_tool TO current_user` so the application's own login can `SET ROLE` to it.
- Privileges: `GRANT USAGE ON SCHEMA public` and `GRANT SELECT` on exactly `packs`, `team_members`, `documents`, `document_parts`, `units`. Nothing else: no INSERT/UPDATE/DELETE anywhere, no access to `users`, `runs`, `findings`, `evidence`, `llm_calls`, `reviews`, `audit_log` or any other table.
- `ENABLE ROW LEVEL SECURITY` (not `FORCE`, so the owner used by migrations, ingestion and tests is unaffected) on those five tables, each with one policy `FOR SELECT TO cda_tool`:
  - `team_members`: `user_id = cda_current_user()`
  - `packs`: the pack's `team_id` is one of the user's teams
  - `documents`, `document_parts`, `units`: their pack (via `documents.pack_id`) is visible as above
- Helper `cda_current_user() RETURNS uuid`: `NULLIF(current_setting('cda.user_id', true), '')::uuid`, `STABLE`. A missing or empty setting gives NULL, so every policy is false (**fail closed**).
- Policies do not look at `deleted_at`; soft-delete filtering stays in the tool queries.
- Downgrade drops the policies, disables RLS, revokes the grants, drops the function, and drops the role only if no other object still depends on it (`DROP ROLE IF EXISTS` inside an exception-guarded `DO` block so a role shared by another database does not break the downgrade).

## `tools/rls.py`
`async with tool_scope(conn, user_id, timeout_s):` opens a savepoint (`conn.begin_nested()`), then runs `SET LOCAL ROLE cda_tool`, `SELECT set_config('cda.user_id', :uid, true)` and `SET LOCAL statement_timeout = <timeout_s in ms>`; on exit it **always rolls the savepoint back** (tools never write, so nothing is lost), which also undoes the role, the setting and the timeout. Errors inside the block propagate after the rollback.

## `run_tool` change
After argument validation, the handler runs inside `tool_scope(ctx.conn, ctx.user_id, ctx.timeout_s)`. A Postgres statement timeout (`QueryCanceledError` / SQLSTATE `57014`) maps to the `timeout()` envelope like the existing `asyncio.wait_for` timeout. T08's team join in every query stays (D29 and D61 are two layers, not alternatives).

## Failing tests to write first (strict: every case its own test, seen failing first; all `db`)
Fixture: as in T08 — teams A and B, users `sarah` (A) and `alex` (B), a pack, documents, a part and units in each team.

Role and privileges:
1. After `upgrade head`, role `cda_tool` exists, is `NOLOGIN`, and the connecting user is a member
2. As `cda_tool` (inside `tool_scope`), `SELECT` from `users`, `runs`, `findings`, `evidence`, `llm_calls`, `reviews`, `audit_log` → permission denied, each table its own parametrised case
3. As `cda_tool`, `INSERT`, `UPDATE` and `DELETE` on each of the five readable tables → permission denied
4. `upgrade head` is idempotent with respect to the role: `downgrade 0004_unit_seq` then `upgrade head` again works, and running the upgrade when `cda_tool` already exists does not fail

RLS:
5. In `tool_scope` with `sarah`: `packs`, `documents`, `document_parts`, `units` return only team-A rows; `team_members` returns only sarah's rows
6. In `tool_scope` with `alex`: only team-B rows
7. As `cda_tool` with no `cda.user_id` set, and with it set to `''` → zero rows from all five tables (fail closed)
8. A user who belongs to no team → zero rows
9. Removing sarah from team A mid-test → her next `tool_scope` sees no team-A rows
10. The owner connection outside `tool_scope` still sees all rows (RLS not forced; ingestion and migrations unaffected)

Scope behaviour:
11. After `tool_scope` exits normally, `current_user` is the original role and `current_setting('cda.user_id', true)` is empty/NULL; same after an exception inside the block (the exception still propagates)
12. Nested use on the T08 test connection (already inside a transaction) works and leaves the outer transaction usable
13. A statement exceeding the scope's `statement_timeout` (e.g. `pg_sleep`) raises inside the scope; through `run_tool` it becomes the `timeout` envelope with `retryable=True`

Defence in depth:
14. With the T08 permission clause monkeypatched to always true (`visible_pack_clause` → `true()`), `keyword_search`, `read_unit` and `list_documents` run by `alex` against sarah's pack still return no team-A data (`forbidden` or `not_found`, never team-A text) — RLS alone blocks it
15. All existing T08 tool tests pass with tools now executing as `cda_tool`

## Done when
- all tests above pass with Docker; ruff, ruff format, mypy (strict), pytest clean
- `alembic upgrade head` and `downgrade 0004_unit_seq` work on the compose database (user `cda`)

## Do not
- remove or weaken the T08 team join in any tool query
- use `FORCE ROW LEVEL SECURITY`, a separate login/password for `cda_tool`, or a second database connection
- add policies or grants for write paths (API, worker, review) — those run as the owner and are checked in application code (T20)
- add RLS to tables the tools do not read
