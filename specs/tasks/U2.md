## How the API maps to PRD 6.3
- Upload stores **and parses** the PDF in the request (`ingest_pdf`), so scanned, encrypted and broken files are rejected at upload with 422 `no_text_layer` / `encrypted` / `invalid_pdf` / `too_many_pages` / `page_timeout`. They never appear in the list.
- "Parse" (`POST /packs/{id}/parse`) builds the search index in the background. A document's `index_status` is `pending` → shown "Not parsed", `indexing` → "Parsing", `done` → "Parsed", `failed` → "Parse failed".
- Pack status (new, computed in the API): no documents → `empty`; any `indexing` → `parsing`; all `done` → `parsed`; some `failed`, rest `done` → `parsed_with_issues`; all `failed` → `parse_failed`; otherwise → `uploaded`.
- The PRD's per-page parse progress ("Page 34 of 212") is not available: indexing reports per document only. The page polls every 2 s while the pack is parsing, so a refresh keeps showing the server's state.
- The New check button moves to U3 with the dialog it opens.

## Backend additions
- `GET /packs/{id}` adds `status`, `team {id, name, members}`, `limits {max_upload_mb, max_documents}`, `active_run_id` (a `queued` or `running` run, else null). `GET /packs` rows add `status` (REST only; MCP output unchanged).
- `POST /packs/{id}/documents`: 409 `pack_full` when the pack already holds 20 documents; 409 `pack_parsing` while the pack is indexing.
- `DELETE /packs/{id}/documents/{did}`: 409 `run_active` while a run on the pack is queued or running.
